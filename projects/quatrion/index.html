The engineering problem

Engineering questions depend on geometry, assembly relationships, and physical behavior. A language model needs usable spatial context and access to engineering tools to help investigate those questions.

I’m building Quatrion to connect natural-language requests with CAD and simulation services. My work brings together spatial representation, agent orchestration, solver development, and deployment infrastructure for manufacturing workflows.

Spatial tokenization

I developed a spatial tokenization concept to bridge LLMs and CAD. It represents CAD parts, assembly hierarchy, positions, orientations, and relationships as structured context that agents can retrieve for a particular engineering question.

Bounded knowledge graphs organize that context. Relevant parts and neighboring relationships can be selected without passing an entire model into every interaction. Source provenance connects the context to the underlying engineering information.

The goal is to make spatial questions answerable through a combination of language-model interpretation and computed engineering evidence. Spatial tokenization is a central technical contribution within Quatrion.

Directing agents through engineering work

I use Codex and Claude Code for implementation and review, with reusable skills, repository guidance, and an architecture knowledge base. Knowledge-graph grounding supplies shared context; multi-agent debate supports review of proposed implementations.

I directed coding agents on Python-to-C++/CUDA FEA refactoring for NVIDIA GPUs. Separately, Quatrion’s native CAD and spatial runtime includes optional CUDA components and CPU/GPU comparison tests. Integration of that runtime is ongoing, with compatibility and numerical behavior part of validation.

My role includes setting the engineering direction, decomposing the work, reviewing agent output, and connecting changes across services. A successful code generation step is followed by integration and verification.

Structural analysis, CFD, and forming

Custom finite element analysis

The FEA work uses FEniCSx and PETSc for linear and nonlinear structural analysis, including large deformation and J2 plasticity. Analytical benchmark tests and convergence reporting support investigation of solver behavior.

CFD and sheet-metal forming

Additional work covers CFD case validation, job management, and postprocessing, plus OpenRadioss integration for sheet-metal forming. These services include asynchronous jobs and extraction of results that the application can present to engineers.

Execution readiness and result provenance matter: a preview and a completed solver result carry different meanings. The platform’s services surface that distinction as these capabilities develop.

Deployment and verification

Containerized services use Kubernetes and Helm with cloud and on-premises deployment targets. Automated checks cover service contracts, deployment configuration, and authentication boundaries. Reusable engineering patterns help coordinate changes across repositories.

Validation spans software tests, numerical benchmarks, CPU/GPU comparisons, and integration checks. Each answers a different question about correctness or readiness. Performance and numerical claims need measurements for the specific implementation and workload.

Quatrion remains in development. Current work focuses on connecting the spatial context, native runtime, simulation services, and agent workflows into repeatable engineering experiences.

Quatrion’s repositories are private. This case study provides a public overview of the work.
