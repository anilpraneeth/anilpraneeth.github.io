A complete learning workflow

I built a private application for two learners, covering reading and mathematics through interactive lessons and parent review. The implemented curriculum spans four courses and 48 chapters, with practice, review activities, and checkpoints.

The product needed more than generated lessons. It needed clear progression, usable interactions, dependable saved work, and a way for a parent to review progress. Those requirements shaped both the interface and the application architecture.

Authored learning with bounded AI support

The application uses React, TypeScript, and Vite, with structured lesson content and dedicated renderers. Amazon Bedrock supplies activity-specific tutoring support, while authored guidance remains available when the model or network is unavailable.

A server-side adapter validates requests and structured responses. Credentials stay out of the browser, and controls limit request size, concurrency, and execution time. Strict-schema checks reject malformed or lesson-incompatible outputs before they reach the learning flow.

Prerecorded Amazon Polly narration plays locally, with browser speech available as a fallback. The core experience can continue when optional AI support is unavailable.

How I used coding agents

I coordinated parallel Codex agents for implementation and review across an AI-assisted software development lifecycle. Work covered interface behavior, backup restoration, loading resilience, and resuming lessons.

Changes were integrated through pull requests, automated checks, and browser verification. My contribution was to define the product needs, divide the work, review behavior, and connect the changes into a usable application.

Using agents across these tasks made integration discipline especially important: shared expectations for content, persistence, and completion had to remain consistent across the product.

Reliability as a product feature

Each learner has isolated, versioned local records. Unfinished drafts are checked against lesson versions and kept separate from completed learning evidence. Retryable saves avoid duplicate progress, and backup restoration includes a preview and per-learner confirmation.

Several design choices make the application more dependable:

  • Separate progress from mastery evidence. Visiting an activity or saving an unfinished draft does not by itself establish mastery.
  • Keep a working fallback. Authored guidance and local narration preserve the learning flow during model or network failures.
  • Make recovery visible. Validated lesson resume, retryable writes, and restoration previews give users a way to recover their work.

What I verified

A recorded September 2026 validation run passed 682 software tests, along with lint and production-build checks. Browser verification covered application flows, including lesson resume.

The tests cover application behavior and data integrity, including malformed tutoring responses and outputs incompatible with the active lesson. These are software validation results; educational effectiveness and model behavioral evaluation require their own evidence.

The repository is private. This overview shares the architecture and engineering approach without exposing learner records.
